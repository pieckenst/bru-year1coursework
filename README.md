# Курсовой проект: Учет продаж проездных билетов

Этот репозиторий содержит курсовую работу **первого курса** Белорусско-российского университета по дисциплине «Основы алгоритмизации и программирования» на тему: **разработка программы учета продаж проездных билетов**. В рамках развития проекта добавлен расширенный функционал для курсовой работы **второго курса** по теме: **разработка информационной системы отдела кадров**.

**Технологический стек проекта:**
- **C#** — основная реализация бизнес-логики, административные и клиентские интерфейсы (Avalonia UI, .NET MAUI, WinForms)
- **Rust + Slint** — современный кроссплатформенный интерфейс для Linux с нативной производительностью и элегантным дизайном
- **Java** — отдельные вспомогательные компоненты и учебные модули

Проект представляет собой комплексное решение, включающее настольные, мобильные и административные приложения, а также серверную часть с REST API и библиотеки для построения динамических форм.

**Философия проекта:**  
Код выложен с образовательными целями для ознакомления с современными технологиями разработки программного обеспечения. Это открытая площадка для студентов и разработчиков, где можно свободно изучать, копировать и использовать код в своих проектах. Основной язык проекта — русский, комментарии в коде на английском языке, что соответствует принятым в индустрии стандартам.попадаются русскоязычные комментарии где английским языком я не могу обьяснить вещи

## Описание

**Цель проекта** — создание комплексного решения для автоматизации учета и управления продажами проездных билетов в автотранспортных предприятиях. Система охватывает полный цикл работы с билетами: от учета и продаж до формирования отчетности и аналитики.

### ⚠️ Важное замечание: Почему это корпоративная система

**Тема курсовой работы первого курса:** "Разработка программы учета продаж проездных билетов"

Эта формулировка темы **изначально подразумевает корпоративную систему**, а не "простое" приложение. Сама постановка задачи "учет продаж проездных билетов" делает невозможным создание упрощенной версии, потому что **не существует такого понятия как "простая система продажи билетов"** для реального использования в организации.

**Почему тема курсовой работы неизбежно требует корпоративного решения:**

Формулировка "учет продаж проездных билетов" автоматически включает в себя:
- **"Учет"** — требует базы данных, отчетности, аналитики
- **"Продаж"** — требует многопользовательского доступа, ролей, кассовых операций
- **"Проездных билетов"** — требует маршрутов, расписаний, автопарка, остановок

Любая функциональная реализация этой темы неизбежно требует полного набора корпоративных функций. Попытка упростить систему приводит к нефункциональному продукту, непригодному для практического использования. Вот почему:

1. **Масштаб данных**
   - В реальной базе данных: **72,180 записей расписаний**
   - Необходимость обработки **145 страниц API** (по 500 записей на страницу)
   - Это не "простая" база данных — это корпоративный объем данных

2. **Сложность маршрутов**
   - Многоостановочные маршруты с различными вариантами следования
   - Сезонные изменения и временные объезды
   - Связь маршрутов с остановками, расписаниями и автобусами
   - Невозможно упростить без потери функциональности

3. **Продвинутое управление расписаниями**
   - Повторяющиеся расписания с паттернами дней недели
   - Диапазоны дат действия расписаний
   - Исключения для праздников и особых дней
   - Фильтрация по датам с учетом дней недели
   - Это не "простая" логика — это сложная бизнес-логика

4. **Требования к производительности**
   - Необходимость пагинации для обработки тысяч записей
   - Интеллектуальное кэширование для мгновенного доступа
   - Оптимизация UI для плавной работы с большими данными
   - Без этого система будет непригодна к использованию

5. **Управление автопарком**
   - Назначение автобусов на маршруты
   - Планирование работы водителей
   - Отслеживание технического обслуживания
   - Учет состояния транспорта
   - Это неотъемлемая часть любой транспортной системы

6. **Многопользовательская архитектура**
   - Ролевой доступ (администраторы, кассиры, диспетчеры)
   - Одновременная работа нескольких пользователей
   - Согласованность данных при конкурентных операциях
   - Без этого система не может использоваться в организации

**Вывод:** Данный проект **не эволюционировал** из простой системы в корпоративную — он **изначально был корпоративной системой** по определению темы курсовой работы. Формулировка "разработка программы учета продаж проездных билетов" физически невозможна без полного набора корпоративных функций. Это не "раздувание" проекта — это **минимальный набор функций**, необходимый для выполнения поставленной задачи.

**Образовательная ценность:** Этот проект демонстрирует студентам важный урок — **формулировка задачи определяет масштаб решения**. Тема "учет продаж проездных билетов" изначально подразумевает корпоративную систему, потому что такая задача не может быть решена "просто". В реальном мире не существует "простых" систем учета продаж — любая практическая реализация требует комплексного подхода и корпоративного уровня разработки.

**Практическое доказательство:** Rust UI успешно обрабатывает 72,180 записей расписаний через 145 страниц API — это реальные данные из реальной системы, демонстрирующие, что даже "учебный" проект требует корпоративных решений для работоспособности.

### 📋 Расширение системы: HR-модуль для курсовой работы второго курса

**Тема курсовой работы второго курса:** "Разработка информационной системы отдела кадров"

Система получила **значительное расширение функционала** для выполнения требований курсовой работы второго курса. Как и в случае с первым курсом, тема "информационная система отдела кадров" **изначально подразумевает корпоративное решение**, а не упрощенную систему.

**Почему HR-система также требует корпоративного подхода:**

Формулировка "информационная система отдела кадров" автоматически включает:
- **"Информационная система"** — требует полноценной базы данных, интеграции с существующими системами, безопасности данных
- **"Отдела кадров"** — требует управления всем жизненным циклом сотрудников, документооборота, соответствия трудовому законодательству
- **Интеграция с транспортной системой** — сотрудники являются водителями, кассирами, диспетчерами — необходима связь с маршрутами, автобусами, расписаниями

**Реализованный HR-функционал:**

1. **Управление сотрудниками (23 поля данных)**
   - **Основная информация:** ФИО, должность, отдел, дата приема на работу
   - **Личные данные:** паспортные данные (серия, номер), контакты (email, телефон), адрес, СНИЛС
   - **Водительские права:** номер ВУ, категория, дата окончания действия
   - **Медицинская справка:** номер справки, дата окончания действия
   - **Связь с транспортной системой:** назначение водителей на автобусы и маршруты

2. **Управление должностями**
   - Создание и редактирование должностей
   - Определение обязанностей и требований
   - Связь должностей с правами доступа в системе
   - Иерархия должностей (водитель, старший водитель, диспетчер, администратор)

3. **Управление отделами**
   - Структура предприятия (отдел эксплуатации, отдел кадров, бухгалтерия)
   - Назначение руководителей отделов
   - Распределение сотрудников по отделам

4. **Интеграция с транспортной системой**
   - **Водители ↔ Автобусы:** назначение водителей на конкретные автобусы
   - **Водители ↔ Маршруты:** планирование работы водителей по маршрутам
   - **Контроль документов:** отслеживание сроков действия водительских прав и медицинских справок
   - **Техническое обслуживание:** связь механиков с графиком ТО автобусов

**Почему это не "простое" дополнение:**

Добавление HR-модуля потребовало:
- Расширения базы данных с сохранением целостности данных
- Обработки циклических ссылок (сотрудник → отдел → руководитель → сотрудник)
- Интеграции с существующей системой прав доступа
- Обработки 23 полей данных для каждого сотрудника
- Валидации документов (паспорта, ВУ, медсправки)
- Связи HR-данных с операционными данными (маршруты, автобусы, расписания)

**Результат:** Система стала **полноценной корпоративной ERP-системой** для транспортного предприятия, объединяющей:
- Управление транспортом (маршруты, расписания, автобусы)
- Управление персоналом (сотрудники, должности, отделы)
- Продажи билетов (кассовые операции, отчетность)
- Техническое обслуживание (планирование ТО, учет ремонтов)

Это демонстрирует, что **реальные корпоративные системы всегда интегрированы** — невозможно создать изолированную "простую" HR-систему для транспортного предприятия, потому что HR-данные неразрывно связаны с операционной деятельностью.

**Основные возможности:**
- Полноценный учет продаж и движения билетов
- Гибкая система управления пользователями и правами доступа
- Автоматизированное формирование отчетности
- Поддержка различных типов билетов и тарифов

**Техническая реализация:**
- **Кроссплатформенные интерфейсы** на базе современных технологий:
  - Avalonia UI (основная платформа)
  - .NET MAUI (мобильное приложение)
  - WinForms (легаси-версия)

- Вынесение бизнес-логики в переиспользуемые сервисы и библиотеки

**Эволюция проекта:**
Первоначально в рамках курсового проекта для учебного заведения было разработано приложение на WinForms в виде минимальной заготовки которое ближе к срокам сдачи было сделанно до конца , основной же фокус сразу был на современном интерфейсе Avalonia. В процессе развития были добавлены:

3. Заготовка мобильного приложения `TicketSalesAPP.Mobile.UI.MAUI`

**Планы по развитию:**

2. Реализация мобильного приложения с функциями:
   - Аутентификация по QR-коду

   - Удобная система ролей и прав доступа

Проект продолжает активно развиваться и может быть использован в качестве основы для дальнейших исследований и разработок в области транспортной логистики и автоматизации продаж.

## Основные компоненты и папки

### SuperNova (и подмодули: SuperNova.Runtime, SuperNova.Desktop, SuperNova.Standalone)
**SuperNova** — это современный административный интерфейс на Avalonia, предоставляющий:
- визуальный редактор форм и отчётов
- расширенное администрирование пользователей и маршрутов
- систему поиска и фильтрации данных
- поддержку динамических форм (через собственный движок)
- тестовые и демонстрационные режимы для обучения

Имя SuperNova было выбрано не случайно — этот модуль действительно можно сравнить с космическим взрывом в процессе разработки. В буквальном смысле, код неоднократно "взрывался" во время выполнения, вызывая критические ошибки и неожиданные падения. 

Данный модуль представляет собой современный интерфейс для администрирования и управления системой, который до сих пор находится в крайне нестабильном состоянии. Изначально разрабатывавшийся как закрытый проект, он содержит множество экспериментальных функций и недокументированных возможностей.

Особенности текущего состояния:
- В коде остались артефакты отключенного VB6 интерпретатора, что создает дополнительные риски при модификации
- Наблюдаются проблемы с утечками памяти и переполнением стека (stack overflow)
- Некоторые модули содержат недокументированные зависимости и "костыли"
- Временами возникают проблемы с производительностью при работе с большими объемами данных
- Отсутствует полный набор автоматических тестов

В связи с этим, данную версию программы административного интерфейса следует рассматривать как альфа-версию, не предназначенную для промышленной эксплуатации. Кодовая база может быть кардинально изменена в любой момент без сохранения обратной совместимости. Разработчикам рекомендуется проявлять особую осторожность при работе с этим модулем и всегда сохранять резервные копии перед внесением изменений.Стабильный графический интерфейс находится в проектах TicketSalesApp.UI.LegacyForms.DX.Windows и TicketSalesApp.UI.Avalonia а также TicketSalesApp.UI.Administration.Avalonia а SuperNova это эксперементальный вариант

## ⚠️ Важное примечание о Legacy WinForms версии

Проект содержит модуль `TicketSalesApp.UI.LegacyForms.DX.Windows`, который был создан исключительно для выполнения формальных требований университетской программы. Данная реализация использует устаревшую технологию Windows Forms (выпущенную в 2002 году) с элементами управления DevExpress и имеет ряд фундаментальных ограничений, присущих самой платформе:

### 🔧 Технические ограничения Windows Forms

1. **Архитектурные проблемы**
   - Одно-поточная модель (STA) создает узкие места в производительности
   - Отсутствие современной системы привязки данных (data binding)
   - Устаревшая модель событийного программирования
   - Ограниченная поддержка асинхронных операций
   - Невозможность корректной работы с современными API и протоколами

2. **Проблемы с памятью**
   - Документированные утечки памяти в базовых контролах
   - Проблемы с освобождением ресурсов GDI+ (дескрипторы GDI)
   - Утечки при динамическом создании/удалении контролов
   - Ограниченный контроль над жизненным циклом объектов

3. **Ограничения интерфейса**
   - Примитивная система валидации ввода
   - Отсутствие встроенной поддержки MVVM
   - Ограниченные возможности кастомизации внешнего вида
   - Проблемы с рендерингом сложных элементов интерфейса

4. **Проблемы с масштабированием (DPI)**
   - Плохая поддержка высоких DPI мониторов
   - Размытие интерфейса при масштабировании
   - Проблемы с позиционированием элементов
   - Ограниченная поддержка различных разрешений экрана

5. **Отсутствие доступности**
   - Минимальная поддержка стандартов доступности
   - Плохая работа с программами чтения с экрана
   - Ограниченная поддержка клавиатурной навигации
   - Несоответствие современным стандартам юзабилити

6. **Безопасность**
   - Устаревшие механизмы аутентификации
   - Ограниченная поддержка современных стандартов шифрования
   - Уязвимости, присущие устаревшим компонентам

### 🔍 Почему это не ошибки в коде

Упомянутые проблемы являются фундаментальными ограничениями платформы Windows Forms, а не недостатками конкретной реализации. Как видно из кода предупреждения в `Program.cs`, приложение явно уведомляет пользователя об этих ограничениях:

```csharp
// Показать предупреждение об устаревшем приложении
XtraMessageBox.Show(
    "ПРЕДУПРЕЖДЕНИЕ: Это устаревшее приложение Windows Forms с множеством недостатков..."
    // ... остальной текст предупреждения
);
```

### 🚀 Рекомендуемая альтернатива

Современные альтернативы, такие как **Avalonia**, лишены этих проблем благодаря:
- Современной архитектуре рендеринга на базе DirectX/Vulkan
- Полноценной поддержке асинхронности
- Встроенной системе привязки данных
- Поддержке MVVM из коробки
- Нативной кроссплатформенности
- Открытому исходному коду и активному сообществу

**Важно:** Для промышленной эксплуатации настоятельно рекомендуется использовать современные интерфейсы на базе Avalonia, идущие в комплекте с проектом.

## Ключевые достижения проекта

### 🎯 Доказательство концепции

Этот проект успешно доказывает несколько важных концепций:

1. **"Простых" систем не существует**
   - Первоначальная задача: "простая система продажи билетов"
   - Реальность: корпоративная система с 72,180+ записями расписаний
   - Урок: любая практическая система требует корпоративного подхода

2. **Rust для корпоративных приложений**
   - Эффективная обработка 72,000+ записей
   - Память-безопасность без сборщика мусора
   - Нативная производительность на Linux
   - Современный UI с Slint Framework

3. **Масштабируемая архитектура**
   - Обработка 145 страниц API
   - Интеллектуальное кэширование
   - UI пагинация для плавной работы
   - Клиентская фильтрация больших данных

### 📊 Технические метрики

**Обработка данных:**
- 72,180 записей расписаний
- 145 API запросов при первой загрузке
- ~20MB кэш в памяти
- < 1мс доступ к кэшированным данным

**Производительность UI:**
- Пагинация по 100 элементов
- Плавная прокрутка тысяч записей
- Мгновенная реакция на действия пользователя
- Отсутствие зависаний

**Архитектура:**
- 3 различных UI фреймворка (WinForms, Avalonia, Rust+Slint)
- RESTful API с правильной пагинацией
- Обработка циклических ссылок (ReferenceHandler.Preserve)
- Кроссплатформенность

Проект демонстрирует студентам:

1. **Реальность разработки ПО**

   - Необходимость оптимизации производительности
